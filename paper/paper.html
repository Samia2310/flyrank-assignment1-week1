Content Opportunity Scoring

A transparent baseline, leakage audit, and ranked content-review workflow

Author: Samia Tabassum Chowdhury · Lane: Refresh / Content Opportunity Scoring

Abstract

This project asks which content pages should receive review or refresh attention based on observed search-performance and freshness signals. I first built a transparent baseline using content freshness, search visibility, and click-through rate, then evaluated a Random Forest model using the same action proxy. The initial random-split model reached 0.9998 accuracy, but a validation audit showed that this score was inflated because the model included features used directly to construct the action label. After removing those label-generating features and evaluating with a client-grouped split, accuracy fell to 0.6633. The resulting system is therefore best framed as directional decision-support: it can prioritize pages for human review, but it does not establish causal refresh impact or prove that a page will improve after editing.

1. Introduction / Problem Statement

Content teams often have more pages to review than they can inspect manually. The decision supported by this project is therefore which pages should be reviewed first.

The baseline uses three transparent signals: staleness (days_since_last_update ≥ 180), visibility (impressions_90d ≥ 500), and low CTR (ctr < 1.0). The goal is not to automate publishing or guarantee a performance lift. It is to create a repeatable queue that helps a human reviewer focus attention where the observed signals are strongest.

2. Data

The Week-4 notebook loaded content_refresh_anonymized.csv with 30,000 rows and 44 columns. The working fields include content identifiers, search-demand fields, content metadata, historical impressions/clicks/sessions, freshness measures, CTR, average position, engagement, scroll behavior, and trend fields.

The exact warehouse release/date window is not explicitly restated in the W05–W07 result material, so this paper does not invent a more specific release or date range. The public-safe analysis excludes client names, domains, private queries, credentials, and raw private exports.

3. Methodology

Baseline

  • +2 stale
  • +2 visible
  • +1 low CTR

Score 5 → Refresh Immediately; score 3–4 → Review Soon; score 0–2 → Monitor.

Reason codes: stale_but_visible, stale_content, low_ctr, healthy.

Model

A Random Forest Classifier was used as the machine-learning alternative. The original feature set included freshness, impressions, CTR, content age, search volume, average position, engagement rate, and scroll rate.

Validation and leakage

The action label was itself constructed from freshness, impressions, and CTR. Including those same fields as model inputs allowed the model to recover the label-generating rule. The validation audit therefore removed those three fields and used a client-grouped split, preventing the same client from appearing in both training and test data.

5. Limitations & Honest Framing

  • The action label is a hand-built proxy, not ground truth for content quality or business value.
  • The original random-split score was inflated by target leakage.
  • Client grouping is more conservative, but it is not a substitute for a true time-forward evaluation.
  • Search intent, seasonality, content quality, business priority, competitor changes, and algorithm changes are not fully represented.
  • No causal claim is made about refreshing content or changing Google rankings.

7. Human Review & No-Go List

Human review is required before action. The system should never automatically publish, overwrite, delete, merge, or make causal claims about search performance. A low CTR is not proof of poor content.

8. Monitoring / Retrain Triggers

  • Input schema changes
  • Material distribution shifts in CTR, impressions, or freshness
  • New content types or clients outside the evaluated population
  • Unexpected changes in action mix
  • Declining performance on a newly held-out period
  • Changes to the business definition of “refresh”

A future version should use a true time-aware evaluation and a clean future outcome label whose window starts strictly after the feature window.
